## A. Mobile Google sign-in (server flow + deep link)

### Today
- identity already runs the whole Google flow server-side with PKCE: `POST /auth/oauth/google/start` (`ID/presentation/http/OAuthController.java:90`, Origin check, sets correlation cookie `__Secure-weav_oauth_tx` + `XSRF-TOKEN`), `GET /auth/oauth/google/callback` (`:106`, needs the correlation cookie + `state`, 303 to the return target with `?transaction_id=&handoff_code=` or `&oauth_error=`), `POST /auth/oauth/exchange` (`:152`, Origin + CSRF, verifies `S256(codeVerifier)` against the stored challenge, one-use handoff with 60 s TTL and 5 proof failures max; LOGIN returns the access token in the body and the refresh token ONLY as cookie `__Secure-weav_refresh`).
- `OAuthFlowCoordinator` (`ID/application/usecase/OAuthFlowCoordinator.java`) creates state/nonce/provider verifier, stores fingerprints in Valkey, issues the handoff (`:104`, `:290`).
- Single client only: `clientId="web"`, `returnTargetId="web"` hard-coded (`ID/infrastructure/config/OAuthProperties.java:332-340`; `registration()` throws for anything else, `OAuthFlowCoordinator.java:317-327`); `OAuthConfiguration.webClient()` is one `Optional`.
- `OAuthUriPolicy.requireRedirectUri` (`ID/application/validation/OAuthUriPolicy.java:16-28`) accepts only http(s) (http only on loopback): `weav://` fails. `OAuthProperties.validateAndBuild` also requires the return target origin to be in `allowedOrigins`.
- Scopes `openid email profile` (`GoogleOidcAdapter.java:76`). Env: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` (backend callback, registered in Google Cloud), `OAUTH_WEB_RETURN_TARGET_URI`, `OAUTH_WEB_ALLOWED_ORIGIN` (`.env.example:250-260`). Not to be confused with the workspace Connection OAuth (`GOOGLE_OAUTH_*`, workspace-service).
- Gateway has NO OAuth route (`services/api-gateway/src/identity/identity.module.ts`); its `forward()` does not pass Origin/Cookie, uses `redirect:'error'`, requires JSON responses and does not relay `set-cookie`. Public auth paths are rate-limited via `PUBLIC_AUTH_MUTATION_PATHS` (`src/rate-limit/gateway-throttler.guard.ts:26-36`).
- Web calls identity directly (`VITE_IDENTITY_SERVICE_URL`, default `http://localhost:8081`, `apps/web/src/api/auth.api.ts:106-112`, `startGoogleLogin` `:367`, callback page `GoogleOAuthCallbackPage.tsx`).
- Mobile (Expo ~57, expo-router): scheme in `app.json` is `"mobile"`; `expo-web-browser`, `expo-linking`, `expo-secure-store` installed, `expo-auth-session` not needed; login `src/app/(auth)/login.tsx`; auth repo `src/infrastructure/http/http-auth.repository.ts`; gateway base URL `EXPO_PUBLIC_API_BASE_URL`; refresh token stored in SecureStore.

### Design
1. **identity: second client `mobile`.** Registrations become a map by `clientId` (`web`, `mobile`). New property `weav.oauth.mobile.return-target-uri` (env `OAUTH_MOBILE_RETURN_TARGET_URI`, empty = mobile disabled; dev value `weav://auth/callback`). A separate validator accepts a custom scheme ONLY for the mobile return target (scheme allowlist `weav`, no host check against `allowedOrigins`, no query/fragment). `GOOGLE_REDIRECT_URI` and web rules unchanged.
2. **identity: `GET /auth/oauth/google/mobile/start?codeChallenge=&codeChallengeMethod=S256`**, opened by the app in the system browser (`WebBrowser.openAuthSessionAsync`) so the correlation cookie lands in that browser: creates the transaction for client `mobile`, sets the correlation cookie, 303 to Google. No Origin/CSRF (there is no page); rate limit scope `OAUTH_START_IP`.
3. **callback unchanged**: for a `mobile` transaction it 303s to `weav://auth/callback?transaction_id=&handoff_code=` (or `oauth_error=`).
4. **identity: `POST /auth/oauth/mobile/exchange {transactionId, handoffCode, codeVerifier}`**: same handoff + PKCE checks, bound to client `mobile`; LOGIN only (Google LINK stays web, it needs the current password + CSRF); returns `{accessToken, refreshToken, tokenType, expiresIn, user}` in the BODY like `POST /api/auth/login` (no cookies, no CSRF). Account rules identical to web Google login (reuse `CompleteGoogleLoginUseCase`). `SecurityConfig` permitAll + `AuthRateLimitFilter` scope `OAUTH_EXCHANGE_IP`.
5. **gateway: `POST /api/auth/oauth/mobile/exchange`** public JSON route via `forward()`, add to `PUBLIC_AUTH_MUTATION_PATHS`, e2e test.
6. **Decision D-OA1 (proposed, confirm in Week 6): the browser legs (`mobile/start`, `callback`) stay on identity's public URL for now** (the web does the same). Moving them behind the gateway needs a redirect-aware proxy (relay `Location` + `Set-Cookie`), a cookie path change (`/auth` vs `/api/auth`) and a new redirect URI in Google Cloud Console (K's action). Do it with the deployment work.
7. `.env.example`: `OAUTH_MOBILE_RETURN_TARGET_URI=` with comment; mobile needs the identity public URL for the browser leg (`EXPO_PUBLIC_IDENTITY_URL`, handoff).

### Mobile handoff (partner)
Add scheme `weav` in `app.json` (native rebuild, not OTA); generate PKCE verifier/challenge (S256); `WebBrowser.openAuthSessionAsync(<identity>/auth/oauth/google/mobile/start?codeChallenge=...&codeChallengeMethod=S256, 'weav://auth/callback')`; parse `transaction_id`/`handoff_code`/`oauth_error`; `POST /api/auth/oauth/mobile/exchange` through the gateway; store tokens like password login. Device testing: the correlation cookie is `Secure`, so the identity URL must be HTTPS (cloudflared quick tunnel to identity) or localhost; a phone on the LAN over plain http will lose the cookie.

### Acceptance
- identity: integration test mirroring `GoogleOAuthHttpIntegrationTest` for `mobile` (start 303 + cookie, callback 303 to `weav://...`, exchange 200 with refresh token in body, wrong verifier / reused handoff / web client id on mobile exchange rejected, web flow unchanged); `OAuthUriPolicyTest` and `OAuthPropertiesTest` cover the custom scheme and "mobile disabled when the env is empty". `./mvnw verify` green.
- gateway: e2e for the exchange route + rate limit. No new Google scopes.

### Risks
Custom-scheme hijack on Android (mitigated: PKCE verifier stays in the app, 60 s one-use handoff, 5-failure cap; App Links later); single-client assumptions spread across `OAuthConfiguration`, `OAuthWebProtection`, CORS config and many tests; scheme change needs a new native build.

## B. Workspace delete (soft delete + shut down)

### Today
- `Workspace` has no status (`WS/domain/model/Workspace.java`, `WorkspaceJpaEntity`); migrations end at **V6** (`services/workspace-service/src/main/resources/db/migration/`); unique index `ux_workspaces_owner_name_normalized (created_by, name_normalized)`; memberships/connections/credentials cascade from their parent.
- No `DELETE /workspaces/{id}`. Use cases share one shape: transaction -> `mutationLock.lock(workspaceId)` -> `membershipRepository.findByWorkspaceIdAndUserId` (missing = `RESOURCE_NOT_FOUND`, non-owner = `ForbiddenException`), after-commit `authorizationCache.evict` (see `RenameWorkspaceUseCase`, `LeaveWorkspaceUseCase`). `findByWorkspaceIdAndUserId` is the choke point used almost everywhere (incl. connections and `ResolveWorkspaceAccessUseCase` = internal `/access`).
- Connections: `DeleteCredentialUseCase.deleteInTransaction` (wipe + `markDisabled`) exists per connection; all connection mutations go through `ConnectionUsageProtection` (HTTP to workflow-service usage endpoint, blocks if used). `ResolveConnectionUseCase` fails for non-ACTIVE connections.
- Events: workspace-service only publishes notification events (outbox `notification_outbox`, exchange `weav.events`, `WorkspaceNotificationEvent` v2, 1-100 recipients, batching like `recordRenamed`); contract `packages/contracts/events/notification/event-v2.schema.json`; consumer notification-service (`src/domain/notification-event.ts`, `notification-catalog.ts`).
- workflow-service learns nothing by events: it calls `WorkspaceClient.getAccess` per request (`WF/application/service/WorkspaceAuthorization.java`, Caffeine 30 s cache incl. DENIED). Background paths (schedule, Gmail, webhook, workers) never check access.
- Pause = `WorkflowPublicationService.changeStateLocked` (lock, `pause()`, `triggers.setCurrentEnabled(... false ...)`, after-commit `clearUnusedBots` -> `TelegramWebhookPort.unregister`, which resolves the bot token through workspace-service). Schedule/Gmail pollers select ACTIVE triggers + PUBLISHED workflows; webhook rejects unless PUBLISHED + ACTIVE. No bulk pause. The only internal route is `/internal/workspaces/*/connections/*/usage` (`InternalServiceKeyFilter` regex + `SecurityConfig.java:57`).
- Gateway: `services/api-gateway/src/workspace/workspace.controller.ts` (zod, `proxy.forward`), `WorkspaceMethod` already has DELETE; route order matters next to `:workspaceId/members/me`.
- Web: `workspace.api.ts` (`leaveWorkspace` ~493), `WorkspacePage.tsx` (`handleLeave` ~419 = cleanup template; owner text ~688), `components/common/TypedConfirmDialog.tsx` (phrase match, used in `WorkflowsPage.tsx:815`), `FirstWorkspaceCard` for zero workspaces. Mobile: `apps/mobile/src/app/(app)/workspace/index.tsx` (`Confirmation = remove | leave`).

### Design
1. **workspace-service V7**: `status VARCHAR(16) NOT NULL DEFAULT 'ACTIVE'` (CHECK ACTIVE/DELETED), `deleted_at`, `deleted_by`; replace the owner-name unique index with a partial one `WHERE status = 'ACTIVE'` (a deleted name can be reused). Additive.
2. `Workspace.markDeleted(actor, now)`; the membership lookups (`findByWorkspaceIdAndUserId`, `existsByWorkspaceIdAndUserId`), the accessible list + count, `existsOwnedNameNormalized` and the internal connection routes (`/resolve`, `/authorize-attachment`, `/auth-failure`) treat a DELETED workspace as not found. Mutations that take the lock re-check status.
3. **`DeleteWorkspaceUseCase`** (`DELETE /workspaces/{id}`, body `{name}`, 204): lock; OWNER only; normalized name must match (else `BadRequestException`); call workflow-service pause-all FIRST (sync, existing internal key + circuit breaker; failure -> abort with `DependencyUnavailable`/503, nothing changed); then in one transaction: mark DELETED, disable every connection and delete every credential of the workspace (new bulk repository methods, bypassing `ConnectionUsageProtection`), record `workspace.deleted` for the other members (batches of 100, actor excluded as in #32); after commit evict the authorization cache for all members.
4. **workflow-service `POST /internal/workspaces/{w}/pause-all`** (service key; extend the filter regex + `SecurityConfig` matcher): for every PUBLISHED workflow of the workspace: lock, `pause()`, disable current triggers, unregister unused Telegram bots (needs the credential, hence before the wipe); idempotent and retriable; no per-workflow `workflow.paused` notifications; no actor capability check; returns counts. In-flight executions are left to finish or fail on resolve (documented).
5. **gateway** `@Delete(':workspaceId')` with strict body `{ name }` (check the proxy forwards DELETE bodies), e2e test.
6. **contracts + notification-service**: `DELETE` in `packages/contracts/http/workspace/openapi.yaml`; `workspace.deleted` in `event-v2.schema.json` + notification-service event model/catalog + specs; web and mobile notification mapping (target NONE).
7. **web**: `workspaceApi.deleteWorkspace(id, name)` (+ mock branch); OWNER-only "Xóa không gian làm việc" danger zone on the Workspace settings tab using `TypedConfirmDialog` (phrase = workspace name, consequences listed: workflows stop, connections removed, members lose access); cleanup like `handleLeave`; if no workspace remains, the dashboard shows `FirstWorkspaceCard`; i18n VI/EN.

### Mobile handoff (partner)
Repository `deleteWorkspace(id, name)` -> `DELETE /api/v1/workspaces/:id` body `{name}`; OWNER-only confirmation (type the name); after success remove the workspace from the store and fall back to another or the create screen; map `workspace.deleted` notifications.

### Acceptance
- workspace-service tests: owner deletes with the right name (204, hidden from all members' lists, `GET` 404, internal `/access` denied, connections DISABLED, credentials gone, notification rows for other members only); wrong name 400; non-owner 403; pause-all failure aborts with nothing changed; name reusable after delete; V7 on Testcontainers. workflow-service: pause-all pauses only that workspace, disables triggers, idempotent, rejects calls without the service key. Gateway e2e. Web Playwright (stubbed) + browser check on the real stack: delete a throwaway workspace, its Gmail/Telegram/schedule triggers stop (trigger rows DISABLED).

### Risks
Partial failure between services (mitigated: pause-all first, abort on failure, idempotent retry); Telegram unregister is best-effort (the webhook endpoint still rejects disabled triggers); auth caches (Redis evicted for every member; workflow-service Caffeine up to 30 s); the user's last workspace (zero-workspace UI); concurrent mutations (same mutation lock + status re-check).
