# AI Service

NestJS (Fastify) service that Workflow Service calls for AI-backed steps: summarize, classify, extract structured data and workflow generation. It owns its domain rules, validates every request strictly and never persists user content.

Commands: `pnpm test` (unit), `pnpm test:e2e`, `pnpm build`, `pnpm lint`.

## Configuration

| Variable | Default | Description |
| --- | --- | --- |
| `PORT` | `3000` | HTTP listen port. |
| `AI_PROVIDER` | `deepseek` | Provider selector (only `deepseek` is supported). |
| `DEEPSEEK_API_KEY` | — | DeepSeek API key. Blank keeps the service not-ready. |
| `DEEPSEEK_MODEL` | — | DeepSeek model name. Blank keeps the service not-ready. |
| `DEEPSEEK_BASE_URL` | `https://api.deepseek.com` | Provider base URL. |
| `DEEPSEEK_MAX_TOKENS` | `4096` | Per-call token cap (256–8192). |
| `AI_SERVICE_JWKS_FILE` | — | Path to Workflow's JWKS JSON for Service JWT verification. Missing/unreadable keeps the service not-ready. |
| `AI_REQUEST_TIMEOUT_MS` | `60000` | Per-request deadline starting before body parsing (1000–120000). |
| `AI_MAX_CONCURRENCY` | `4` | Global in-flight cap (1–64). |
| `AI_MAX_CONCURRENCY_PER_WORKSPACE` | `2` | Per-workspace in-flight cap (1–64). |

## Readiness

`GET /health/live` is 200 whenever the process runs. `GET /health/ready`
is 200 only when both a provider (API key + model) and a JWKS verifier are
configured; otherwise it is 503 and every `/v1/*` route answers
`AI_NOT_CONFIGURED`. A missing key, model, or JWKS keeps the service up but
not ready, never crashing startup.

## Authentication

Callers present a Workflow-issued RS256 Service JWT (`iss=weav-workflow`,
`aud=weav-ai`, `ai:<operation>` scope, tenant/request binding, ≤120 s
lifetime). The JWKS file holds Workflow's public key and is generated by
`node scripts/ai-dev-keys.mjs` into `tmp/service-keys/public/` (the private
key goes to `tmp/service-keys/private/`). In Compose, ai-service mounts only
the `public/` folder read-only at `/run/weav-keys`; workflow-service mounts
only `private/`.

## Assistant chat (spike)

`POST /v1/assistant/chat` streams an assistant turn as SSE (`delta`, `tool_call`,
`tool_result`, `draft`, `done`, `error`). It exists only when `AI_ASSISTANT_ENABLED=true`.
It accepts **user** access tokens (identity RS256, verified against
`JWT_JWKS_URI` with the gateway's `JWT_ISSUER` / `JWT_AUDIENCE`), never service
JWTs; the service-JWT routes above never accept user tokens. Its tools call workflow-service (`AI_WORKFLOW_API_URL`) and workspace-service
(`AI_WORKSPACE_API_URL`) public APIs with the caller's own bearer token:
`list_workflows`, `explain_run_failure`, `list_failed_runs_today` (fan-out, 4 in
flight, 20 workflows x 20 runs), `list_members` (no emails) and `build_workflow`.
`build_workflow` calls `POST .../workflows/generate`, which never persists: the
full result goes to the client as a `draft` SSE event (never to the model) and
the user must review and save it in the editor. The assistant cannot create,
save, publish or run anything. Reach it through
the gateway at `POST /api/v1/assistant/chat`. Live check against DeepSeek:
`pnpm --dir services/ai-service exec ts-node scripts/assistant-live-check.ts`.

## Tests

No test calls DeepSeek: unit tests use a fake `LlmProvider` and the
provider adapter plus HTTP tests run against a local `node:http` fixture
server or in-process fakes.
